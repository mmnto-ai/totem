# The census corpus — the pin

Charter: `spikes/spine-adopt/DECISION.md` ("SCOPED to this V1 corpus and ruleset") and
ADR-103 § "The inexpressible-pattern routing rule" (mmnto-ai/totem-strategy, "49 of the 226 regex
patterns in the compilation-target census"). Sibling pin: `seed/PIN.md` (the frozen seed-20 records,
pinned the same way).

**Pin:** `694acffbf8f91c6b06c5bdba3d3519707f2448d0` — the spike's own last apparatus commit
(2026-09-01). The four shipped corpora at that commit are the corpus every census number in this spike
was taken against: 500 rules across the four files, 226 carrying a non-empty regex `pattern`, the 226
ADR-103 binds to. One more file rides the pin: the one corpus fixture a pinned rule references
(`87aff037`'s `.totem/tests/test-87aff037d7de47a7.md`, read by the facts step), whose `rule:`
frontmatter the live tree re-keyed to the record hash at `934296aa` without failing any check.

The five files below are **byte-identical copies** under `seed/corpus/`, obtained with
`git show <pin>:<path>` and verified by comparing `git hash-object` of each copy against
`git rev-parse <pin>:<path>` (all five blob oids equal):

| `root/compiled-rules.json`                   | `.totem/compiled-rules.json`                          | `589f3f166623` |

The four corpus blobs sit unchanged at every `main` commit from the pin through `934296aa^`
(2026-10-13). At `934296aa` ("S6 step 7 — the serving file regenerated from the floor file of
record") the root corpus moved to 513 rules and 220 patterns, so the live tree reads 528 and 229 and
the census's intake assertions failed on every run from the 2.16.1 cut onward (fifteen runs; the last
green run 2026-10-12 on a `main` push); the fixture's `rule:` moved in the same commit.

**Why a pin, not a re-count.** The census is a record of the corpus the spike was scoped to, and its
226 is cited by ADR-103 as the compilation-target census; re-pinning the numbers to the live tree
would silently change what the ADR describes, and every later corpus change would break the harness
again. A deliberate move to a newer corpus moves this pin, the five copies and the numbers in
`src/census.mts` together, in one commit, with the ADR citation re-read.

**Why committed copies, not `git show` at run time.** The CI checkout is depth 1 (`actions/checkout`
with no `fetch-depth`), so the pin commit is not in the runner's object store and a run-time
`git show` fails on every CI run. The harness therefore reads the copies (`PINNED_COPIES` and
`pinnedOrLivePath` in `src/lib/spike-env.mts`: a pinned path resolves to its copy and fails loud if
the copy is missing; any other path resolves to the live tree as before), and each repo-relative
path stays the LABEL the committed artifacts record (`corpora[].file`, with the host's separators,
as before), so the artifacts are unchanged. `verify-records.mts` compares the copies against the pin
in the three-way shape `seed/PIN.md` uses: git could not run is a FAILURE; the pin not in this clone
is a SKIP with the reason `pin-commit-not-present-locally` named; the pin present means every copy
is compared, bytes against blob. `.prettierignore` lists `seed/corpus/` so a formatter rewrite cannot
break the identity.

**What the committed verification artifact carries.** `artifacts/records-verification.json` on main is
generated in a full clone, so it carries the CORPUS PIN row in its pin-present form ("the 5 committed
copies … are byte-identical to their blobs at …"); a depth-1 CI arm writes the SKIP row with its
reason named instead. The two can never be byte-identical across clone depth — the same split the
SEED PIN row already has — and no step compares the committed file against a CI regeneration; the
row's name says which clone produced it. The run manifest (`src/manifest.mts`) hashes the pinned
fixture from its copy, so `manifest.fixtures[].sha256` binds the bytes the facts step read.

**Older artifacts regenerated by other steps.** The record-intake reject reason named the record by
its absolute path until 2026-10-16; `artifacts/lowering-rejects.json` is regenerated by `npm run
lower`, and `artifacts/k4-swap/lowering-rejects.json` and `artifacts/k4-swap/records-verification.json`
by the K4 swapped-examples control inside `npm run controls` — until those steps next run and their
output is committed, those files still carry the reason string from the checkout that last produced
them.

**Known reader outside the harness.** `egg-probe/src/main.rs` dereferences the census artifact's
`corpora[].file` labels against the LIVE tree (its `corpora_integrity` check); today every pinned row
still matches the live corpus, so it reports no mismatch, and it does not run in CI. If a pinned row
is ever edited or removed from the live corpus, that probe is where the divergence surfaces first.

**Why the workflow stopped running on tags.** `spine-spike-linux.yml` is `on: push` with a `paths`
filter on this directory; GitHub does not evaluate path filters for tag pushes, so every release
cut's tag pushes (the four package tags and the floating `v0`) ran the harness and failed it on the
stale census. The push trigger now also names `branches: ['**']`, and a workflow with only branches
named does not run for tag pushes; the paths filter governs branch pushes as before.

Verification, from any checkout (the pin need not be present — the copies are what the harness
reads; with the pin present, `verify-records` compares them):

```bash
cd spikes/spine-adopt && npm run census && SPIKE_RECORD_SET=seed20 npm run verify-records
git rev-parse 694acffbf8f91c6b06c5bdba3d3519707f2448d0:.totem/compiled-rules.json   # 589f3f16…, when the pin is present
```
