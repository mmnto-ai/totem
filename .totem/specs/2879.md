### Problem Statement

`totem gate check --event merge-ready` predicate 1 (the status-check floor) reads the PR's GraphQL `statusCheckRollup.contexts` and classifies every `CheckRun` node whose conclusion is not a success as `failing`. The rollup lists EVERY check run on the head, including the run a workflow's `cancel-in-progress` concurrency group cancelled because a later run of the same workflow superseded it. A head with two D1 runs, one `CANCELLED` (superseded) and one `SUCCESS`, read "1 of 16 status checks are failing" at both tiers while `gh pr checks` and GitHub's merge box showed every check green (mmnto-ai/totem#2877 at `46ef1840` and `7d22c1fb`, 2026-09-16). The floor denied a mergeable PR.

### Ruled design (2026-09-18, the seat's call as implementer; the issue's proposal amended by a measurement; one falsification leg folded)

**Judge a check NAME by its latest run; the latest run is the greatest `databaseId`.**

- The `CheckRun` fragment selects `databaseId` beside `name status conclusion`. GitHub's check-run id is one increasing sequence, so among same-named runs on one head the greatest id IS the latest run. The load-bearing claim is exactly the max element: the greatest id is the run that started last — 31 of 31 live same-named groups (60 `main` commits plus the PR heads, leg 1) and 15 of 15 (30 more recent `main` commits, leg 2). Full id order is NOT always full start order within a name (ids are minted at queue time; `main` `9ce020bb` has a lower id that started three seconds after a higher one), and the collapse never needs it. No other field is added: `startedAt` is nullable on a queued run and would need parsing; `checkSuite.app.slug` would widen the fragment for a collision the cohort does not have (see the residual below).
- **The rollup's own order is NOT an ordinal.** The issue proposed "the rollup's own order, which is newest-last" as the fallback. A live read on 2026-09-18 of mmnto-ai/totem#2877's head `46ef1840` listed the LATER D1 run (started 03:44:23Z, id 104657003920) BEFORE the earlier one (03:42:57Z, id 104656726470); mmnto-ai/totem#2871's head lists its pair the other way round. Neither "last listed wins" nor "first listed wins" survives: each would misjudge one of the two real heads, and two fixtures list the greater id in opposite positions so both mutants die.
- **A rerun mints a NEW, greater id, and the rollup keeps only the latest attempt.** The originating incident reconstructs from the Actions attempts API: attempt 1 of run 35052802132 was check run `104656626085` (CANCELLED, started 03:42:25Z) and the superseding run was `104656726470` (SUCCESS); the rerun replaced the cancelled run with `104657003920`. The greatest id at bug time was the SUCCESS, so this read cures the head that surfaced the issue; the spec's ordering specimen above is the post-rerun pair, quoted for the ordering point only.
- **A duplicate group with an unreadable id is an unreadable check state.** If a name ran more than once and any of its runs carries no non-negative-integer `databaseId` (the schema types it nullable, so the arm is reachable), the read returns the UNEVALUABLE class (deny under strict, warn under pilot) naming the check, never a guess at which run is latest. A name that ran once needs no id and is judged on its own conclusion (pinned).
- **Any earlier run is superseded, cancelled or failed.** The collapse judges on the id alone; an earlier `FAILURE` followed by a later `SUCCESS` of the same name passes predicate 1 (a live shape on `main`, where a five-run name begins with a failure). This is what `gh pr checks` shows; the rollup's own `state` (FAILURE on such a head) is read only on the zero-checks arm.
- **`StatusContext` nodes pass through untouched.** Legacy statuses already carry one state per context. A `CheckRun` whose name did not read (`named: false` on the entry; the text is the `(unnamed check)` placeholder; `name` is NON_NULL in the schema, so only a malformed payload reaches it) passes through too, keyed on the read and not on the placeholder text, so two malformed nodes are never read as one check that ran twice and a check really named like the placeholder still collapses (pinned).
- **Counts.** `checks.total` counts names after the collapse, the way `gh pr checks` and the merge box count; `checks.superseded` (new, required on the exported type) counts the replaced RUNS, not names (pinned by a three-run group). The materialisation check (`totalCount` must equal the nodes read) stays on the RAW nodes: the rollup accounts for what it listed, and the collapse is a read of those nodes, run after that check and after the LAST page (pinned by a pair split across two pages).
- **Disclosure.** One stderr line PER collapsed name, sanitised (C0 controls and DEL to spaces, whitespace collapsed) and never sliced: the name, its run count, the judging run's id and kind, and the number of superseded runs. A single line under the 160-character evidence bound lost its tail at three names (the leg found a `main` head with five), and a disclosure that trails off is not one. "Never sliced" is pinned by a fixture whose check name is longer than the bound (the bound itself, `bounded`, is byte-identical to before and still serves every deny reason and `matched`). No sink downstream truncates a notice: the CLI passes stderr through and the hook wrapper re-emits the child's stderr verbatim.
- **The negative that must hold.** A lone `CANCELLED` run with no later run of its name stays `failing`, and a name whose LATEST run is cancelled stays `failing` however many earlier runs of it succeeded.
- **Semver: minor, ruled.** `MergeReadyProvenanceDetail.checks` gains a `superseded` field and `total` now counts names. The type is a record core PRODUCES; every consumer we control reads it (the CLI types `detail` as an opaque record) and none constructs it, so the change is additive at every reader; a hand-constructed value would add one field. Under the repo's rule (no legacy before a consumer we do not control; honest semver) that is a minor, not a major — a removed export or a changed signature would be the major. The fixed changeset group moves every `@mmnto/*` package with it.

### The residual, closed in bot round 1 (Greptile P1)

The first cut keyed the collapse on the name alone and disclosed the residual: two check runs that share a name on one head — two GitHub Apps, or two jobs under one app (Actions names a check run after the JOB) — would collapse to the greater id, so a later success from one producer could hide a failure from the other. Both legs flagged it and the seat disclosed it as unreachable in this repo (every job name distinct across the thirteen workflow files and the four dynamic workflows; over 30 recent `main` heads the only duplicated names were same-job reruns). Greptile's P1 on the round refused that framing on the right ground: the evaluator runs on every consumer repository, where two workflows naming a job `build` or `test` alike is ordinary. Ruled: **the producer is part of the key.** The fragment selects `checkSuite { app { slug } workflowRun { workflow { name } } }`; a run's producer is the app slug joined with the workflow name when the app is Actions (`github-actions/Auto-close guard`), or the app slug alone for another app. Same name and same producer are reruns and collapse to the greatest id (the originating incident: two workflow runs of `Auto-close guard`, one job name, one app). Same name and different producers are independent checks, both judged, so the failure stays a failing check (pinned by a two-workflow fixture that denies naming it). Same name and a member whose producer did not read is an unreadable check state at both tiers — reruns cannot be told from independent checks — never a collapse by name alone (pinned). The capture corpus was re-made a second time in this PR for the new fields.

Greptile's P2 on the same round: an id beyond the safe-integer range is rounded by `JSON.parse`, and two distinct ids rounded to one number would be ordered wrongly. Ruled: the id reader refuses anything that is not a non-negative SAFE integer, as the review-comment id reader already does; a rerun group carrying one such id is unreadable (pinned).
