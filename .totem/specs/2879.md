### Problem Statement

`totem gate check --event merge-ready` predicate 1 (the status-check floor) reads the PR's GraphQL `statusCheckRollup.contexts` and classifies every `CheckRun` node whose conclusion is not a success as `failing`. The rollup lists EVERY check run on the head, including the run a workflow's `cancel-in-progress` concurrency group cancelled because a later run of the same workflow superseded it. A head with two D1 runs, one `CANCELLED` (superseded) and one `SUCCESS`, read "1 of 16 status checks are failing" at both tiers while `gh pr checks` and GitHub's merge box showed every check green (mmnto-ai/totem#2877 at `46ef1840` and `7d22c1fb`, 2026-09-16). The floor denied a mergeable PR.

### Ruled design (2026-09-18, the seat's call as implementer; the issue's proposal amended by a measurement; three falsification legs and one bot round folded)

**Judge a CHECK by its latest run. A check is a name under one producer; the latest run is the greatest `databaseId`.**

- The `CheckRun` fragment selects `databaseId checkSuite { databaseId app { slug } workflowRun { workflow { databaseId name } } }` beside `name status conclusion`. GitHub's check-run id is one increasing sequence, so among reruns of one check on one head the greatest id IS the latest run. The load-bearing claim is exactly the max element: the greatest id is the run that started last — 31 of 31 live same-named groups (60 `main` commits plus the PR heads, leg 1) and 15 of 15 (30 more recent `main` commits, leg 2). Full id order is NOT always full start order within a name (ids are minted at queue time; `main` `9ce020bb` has a lower id that started three seconds after a higher one), and the collapse never needs it. `startedAt` is not selected: it is nullable on a queued run and would need parsing.
- **The producer is part of the key (bot round 1, Greptile P1; the third leg's F1).** A run's producer is the check suite's app slug joined with the WORKFLOW's database id when the app is Actions (`github-actions/317182441`), the app slug alone for another app; for humans the notices show the workflow's display name instead (`github-actions/Auto-close guard`). Only runs that share a name AND a producer are reruns of one check and collapse; two apps, or two workflows, that name a job alike are independent checks, both judged, so a later success never hides an independent failure. The workflow's ID, not its display name, so two workflow FILES that share a `name:` stay apart. An Actions run whose workflow id did not read is a producer that did not read (fail closed), never "every Actions workflow is one producer".
- **Two same-named runs in ONE check suite fail closed (the third leg's F1).** Reruns of a job across two workflow runs sit in two check suites (the originating incident: two runs of `Auto-close guard`, suites 94924978588 and 94925028704; on mmnto-ai/totem#2871 the D1 pair sits in suites 94196705332 and 94208037283 under workflow 317182441); two distinct jobs of ONE workflow run that share a display name sit in one suite. So within a producer, two same-named runs that share a suite id are independent checks the key cannot tell apart, and the group is unreadable at both tiers rather than collapsed; a member with no readable suite id is unreadable the same way. A job re-run inside one workflow run replaces its check run in place and never appears twice in the rollup (the attempts API: attempts 1 and 2 share the suite, only attempt 2's run is listed), so it is not a collision class. Matrix jobs render with their matrix context in the name and are distinct by name.
- **The rollup's own order is NOT an ordinal.** The issue proposed "the rollup's own order, which is newest-last" as the fallback. A live read on 2026-09-18 of mmnto-ai/totem#2877's head `46ef1840` listed the LATER D1 run (started 03:44:23Z, id 104657003920) BEFORE the earlier one (03:42:57Z, id 104656726470); mmnto-ai/totem#2871's head lists its pair the other way round. Neither "last listed wins" nor "first listed wins" survives: each would misjudge one of the two real heads, and two fixtures list the greater id in opposite positions so both mutants die.
- **A rerun mints a NEW, greater id, and the rollup keeps only the latest attempt.** The originating incident reconstructs from the Actions attempts API: attempt 1 of run 35052802132 was check run `104656626085` (CANCELLED, started 03:42:25Z) and the superseding run was `104656726470` (SUCCESS); the rerun replaced the cancelled run with `104657003920`. The greatest id at bug time was the SUCCESS, so this read cures the head that surfaced the issue; the ordering specimen above is the post-rerun pair, quoted for the ordering point only.
- **A rerun group with an unreadable id is an unreadable check state.** If a check ran more than once and any of its runs carries no non-negative SAFE-integer `databaseId` (nullable in the schema, so the arm is reachable; an id beyond 2^53 is rounded by `JSON.parse`, so a safe integer is required — bot round 1, Greptile P2), the read returns the UNEVALUABLE class (deny under strict, warn under pilot) naming the check and its producer, never a guess at which run is latest. A check that ran once needs no id and is judged on its own conclusion (pinned in both directions); two same-named checks from different producers where one lacks an id are both judged (pinned).
- **Any earlier run is superseded, cancelled or failed.** The collapse judges on the id alone; an earlier `FAILURE` followed by a later `SUCCESS` of the same check passes predicate 1 (a live shape on `main`, where a five-run name begins with a failure). The rollup's own `state` (FAILURE on such a head) is read only on the zero-checks arm.
- **`StatusContext` nodes pass through untouched.** Legacy statuses already carry one state per context. A `CheckRun` whose name did not read (`named: false` on the entry; the text is the `(unnamed check)` placeholder; `name` is NON_NULL in the schema, so only a malformed payload reaches it) passes through too, keyed on the read and not on the placeholder text, so two malformed nodes are never read as one check that ran twice and a check really named like the placeholder still collapses (pinned).
- **Counts.** `checks.total` counts checks after the collapse — one per name, one per producer when two producers share a name — the way `gh pr checks` lists them; `checks.superseded` (new, required on the exported type) counts the replaced RUNS, not checks (pinned by a three-run group). The materialisation check (`totalCount` must equal the nodes read) stays on the RAW nodes: the rollup accounts for what it listed, and the collapse is a read of those nodes, run after that check and after the LAST page (pinned by a pair split across two pages).
- **Disclosure.** One stderr line PER collapsed check, sanitised (C0 controls and DEL to spaces, whitespace collapsed) and never sliced: the name and the producer (both JSON-quoted, both untrusted text), the run count, the judging run's id and kind, and the number of superseded runs. A single line under the 160-character evidence bound lost its tail at three names (the first leg found a `main` head with five), and a disclosure that trails off is not one. "Never sliced" is pinned by a fixture whose check name is longer than the bound (the bound itself, `bounded`, is byte-identical to before and still serves every deny reason and `matched`). No sink downstream truncates a notice: the CLI passes stderr through and the hook wrapper re-emits the child's stderr verbatim.
- **The negative that must hold.** A lone `CANCELLED` run with no later run of its check stays `failing`, and a check whose LATEST run is cancelled stays `failing` however many earlier runs of it succeeded.
- **Semver: minor, ruled.** `MergeReadyProvenanceDetail.checks` gains a `superseded` field and `total` now counts checks rather than runs. The type is a record core PRODUCES; every consumer we control reads it (the CLI types `detail` as an opaque record) and none constructs it, so the change is additive at every reader; a hand-constructed value would add one field. Under the repo's rule (no legacy before a consumer we do not control; honest semver) that is a minor, not a major — a removed export or a changed signature would be the major. The fixed changeset group moves every `@mmnto/*` package with it.

### The residual, and what remains

The first cut keyed the collapse on the name alone and disclosed the residual: two check runs that share a name on one head would collapse to the greater id, so a later success from one producer could hide a failure from the other. The seat disclosed it as unreachable in this repo; Greptile's P1 on the bot round refused that framing on the right ground — the evaluator runs on every consumer repository, where two workflows naming a job `build` or `test` alike is ordinary — and the fold keyed on the app slug plus the workflow's display NAME. The third leg (re-armed on that fold) showed "closed" was overstated: two workflow files sharing a `name:`, and two same-named jobs inside one workflow run, still collapsed, and the API exposes the identity fields at the same selection depth. Ruled: the workflow's database ID replaces its name in the key, and two same-named runs of one producer that share a check suite fail closed. What remains, named: a check run whose workflow id or suite id GitHub does not answer is unreadable rather than judged (fail closed, disclosed in the deny reason); whether `workflowRun.workflow` names the CALLER or the CALLEE of a reusable workflow is unverified from a primary source (this repo has no `uses:` job) — if the callee, two callers of one reusable workflow with the same job name would share a producer and, sitting in different suites, collapse; the pinned fixtures do not cover that shape.
