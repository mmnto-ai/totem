### Problem Statement

`totem gate check --event merge-ready` predicate 1 (the status-check floor) reads the PR's GraphQL `statusCheckRollup.contexts` and classifies every `CheckRun` node whose conclusion is not a success as `failing`. The rollup lists EVERY check run on the head, including the run a workflow's `cancel-in-progress` concurrency group cancelled because a later run of the same workflow superseded it. A head with two D1 runs, one `CANCELLED` (superseded) and one `SUCCESS`, read "1 of 16 status checks are failing" at both tiers while `gh pr checks` and GitHub's merge box showed every check green (mmnto-ai/totem#2877 at `46ef1840` and `7d22c1fb`, 2026-09-16). The floor denied a mergeable PR.

### Ruled design (2026-09-18, the seat's call as implementer; the issue's proposal amended by a measurement)

**Judge a check NAME by its latest run; the latest run is the greatest `databaseId`.**

- The `CheckRun` fragment selects `databaseId` beside `name status conclusion`. GitHub's check-run id is one increasing sequence, so among same-named runs on one head the greatest id IS the latest run. No other field is added: `startedAt` is nullable on a queued run and would need parsing; `checkSuite.app.slug` would widen the fragment for a collision the cohort does not have (see the residual below).
- **The rollup's own order is NOT an ordinal.** The issue proposed "the rollup's own order, which is newest-last" as the fallback. A live read on 2026-09-18 of mmnto-ai/totem#2877's head `46ef1840` listed the LATER D1 run (started 03:44:23Z, id 104657003920) at index 1 and the EARLIER one (03:42:57Z, id 104656726470) at index 2, with the other fourteen checks in no chronological order either. "Last listed wins" would have judged the cancelled run on the very head that surfaced the issue. Both mutants ("first listed", "last listed") are pinned dead by fixtures that list the greater id in opposite positions.
- **A duplicate group with an unreadable id is an unreadable check state.** If a name ran more than once and any of its runs carries no non-negative-integer `databaseId`, the read returns the UNEVALUABLE class (deny under strict, warn under pilot) naming the check, never a guess at which run is latest. A name that ran once needs no id.
- **`StatusContext` nodes pass through untouched.** Legacy statuses already carry one state per context.
- **Counts.** `checks.total` counts names after the collapse, the way `gh pr checks` and the merge box count; `checks.superseded` (new, additive) counts the replaced runs, so the record shows what the read saw and set aside. The materialisation check (`totalCount` must equal the nodes read) stays on the RAW nodes: the rollup accounts for what it listed, and the collapse is a read of those nodes, run after that check.
- **Disclosure.** One stderr notice per evaluation names every collapsed name with its run count, the judging run's id and its kind, so a superseded cancel is on the record beside the verdict.
- **The negative that must hold.** A lone `CANCELLED` run with no later run of its name stays `failing`, and a name whose LATEST run is cancelled stays `failing` however many earlier runs of it succeeded.

### Residual, disclosed

Two GitHub Apps that both post a check run under the same name on one head collapse to the run with the greater id, so the later app's run judges the name. The cohort's rollups carry no such pair (every check name on the three heads read on 2026-09-18 is unique per app), the merge box keys required checks by name too, and reading `checkSuite.app.slug` would widen the fragment for every fixture. If a same-name two-app pair ever appears, key the group on (app slug, name) then; the collapse function is the one place to change.
