## Lesson — The core loader turns an unreadable serving file

**Tags:** compile, serving-file, fail-closed, falsification-leg, spine

**Applies-to:** mutator, boundary

**Scope:** packages/core/src/compiler.ts, packages/cli/src/commands/compile.ts

`loadCompiledRulesFile` in core `compiler.ts` (one try block, lines 198-219 at `b0a5b335`) returns an empty rule set for a missing file, throws `TotemParseError` on a Zod schema failure, and on ANY other error (bad JSON, a conflict marker, a BOM, truncation, a 0-byte file, a directory in its place, EACCES) calls its `onWarn` callback and returns empty; the default callback is a no-op. So a guard that reads the serving file through the loader without a throwing callback sees no rows in a file it cannot parse, passes it, and the compile reloads it as empty and overwrites it. B1's first falsification read measured it on mmnto-ai/totem#3039 with a conflict marker before a valid body: the loader warned "is not valid JSON" and returned `{ version: 1, rules: [] }`, and the pre-fold guard let the compile rewrite the file and hash the malformed bytes into the manifest under `--refresh-manifest`. The compile guard since mmnto-ai/totem#3039 reads with an `onWarn` that throws `TotemParseError` (`PARSE_FAILED`) naming the file, before any write and on every path including `--refresh-manifest` and `--export`, and `--allow-record-rows` does not lift it, since an unreadable file could hold record rows. A missing file still compiles; a schema failure still throws from the loader. Any new writer of `compiled-rules.json` reads through the same callback. The one behaviour change a lesson-only repository meets: a corrupt serving file now refuses with two repair routes named (resolve the conflict or restore it from git; or `totem lesson compile` for a lesson-managed file) where it used to be silently regenerated.
