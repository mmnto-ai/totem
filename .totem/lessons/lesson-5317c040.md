## Lesson — A CI job on actions/checkout at its default fetch-depth: 1

**Tags:** ci, shallow-clone, fetch-depth, pin, harness, spike, trap

**Applies-to:** infrastructure

A CI job on `actions/checkout` at its default `fetch-depth: 1` holds ONE commit, so a harness that reads pinned bytes at run time with `git show <pin-sha>:<path>` fails there (`fatal: invalid object name`) even though it passes in every developer checkout, where the pin commit is an ancestor. On mmnto-ai/totem#3095 the first fix of the spike's census pin did exactly that, and the falsification leg reproduced the failure in a shallow clone before CI could. Cure: commit the pinned bytes as copies (`spikes/spine-adopt/seed/corpus/…`, the convention `spikes/spine-adopt/seed/PIN.md` already uses for the seed-20 records); resolve every pinned path to its copy through ONE function (`pinnedOrLivePath` in `spikes/spine-adopt/src/lib/spike-env.mts`) that fails loud when a copy is absent and never falls through to the live tree; and verify each copy against the pin blob (`git cat-file blob <pin>:<path>`, sha256 for sha256) only when the pin commit is present locally, writing a NAMED skip row (`pin-commit-not-present-locally`) otherwise, so a depth-1 arm and a full checkout differ by one disclosed row and never by a verdict. The same class has a squash-merge arm (a harness commit a fresh clone cannot show, a sibling repository's lesson on `git cat-file -e` before a run of record); the rule across both: a run of record never dereferences a commit at run time that the checkout it runs in is not guaranteed to hold.
