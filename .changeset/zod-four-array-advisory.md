'@mmnto/totem': minor
'@mmnto/cli': minor
'@mmnto/mcp': minor

`zod` moves from `^3.24.0` to `^4.6.7` in `@mmnto/totem`, `@mmnto/cli` and `@mmnto/mcp`, so a consumer's lockfile stops resolving `zod@3.25.76`, the version GHSA-mrhx-c7xc-m3w5 (CVE-2023-54404, high) names as vulnerable below 4.6.6, with no patched 3.x release on the registry (mmnto-ai/totem#3141). The advisory's defect is an oversized input against a size-constrained collection: the parser validated every element before the size check ran, so a schema with `.max(10)` still accumulated one issue per failing element; 4.6.6's `capSize` short-circuits at the cap, and an unbounded schema, which declares no cap, parses the same on both majors. Every stored artifact parses to the same result (a differential read of 18,437 on-disk records, 198 schemas and 38 config cases found no difference), and the acceptance set narrows at three edges, each a loud refusal and none hit by existing data: `.datetime()` (nine plain sites and three with `offset: true`) now requires seconds and a colon inside a numeric offset, so `totem legs deposit --read-at 2026-11-02T19:00Z` is refused with "Invalid ISO datetime" where zod 3 accepted it; `z.number()` rejects `Infinity` and `.int()` rejects values above `Number.MAX_SAFE_INTEGER`, reachable only from a TypeScript config; and the exported `DoctorConfigSchema` parsed with no value refuses instead of filling, as the next paragraph says. The single-argument `z.record(value)` form, which zod 4 dropped from its type signature while its runtime keeps a compatibility shim, becomes `z.record(z.string(), value)` at its seventeen sites. The three object-valued config defaults (`review`, `hooks.legsOwed`, `hooks.shield`) move from `.default({})` to `.prefault({})`, because zod 4's `.default()` returns its value without parsing it, and the inner defaults (`sourceExtensions`, `legsOwed.globs`) would no longer fill when the block is absent. The exported `DoctorConfigSchema` loses its block-level default instead: the config attaches it as optional, and zod 4's optional applies an inner default where zod 3 returned `undefined`, so a config that never declared `doctor` would have parsed to a filled block; an empty `doctor: {}` still fills `staleRuleWindow`, and a config without the block still reads `undefined`. The selection manifest's enum-keyed `context` becomes a `partialRecord`, since zod 4's enum-keyed `record` requires every key where zod 3 accepted a subset; it is the only enum-keyed record in the three packages, and every other record is keyed by `z.string()`, where zod 4's semantics are unchanged. The ledger's `session_id` and `correlation_id` and the selection manifest's two session ids move from `.uuid()` to `.guid()`, zod 4's name for the 8-4-4-4-12 hex shape zod 3's `.uuid()` accepted, so a row written by an earlier release still parses (zod 4's `.uuid()` also requires the RFC 4122 variant bits). The three refinements that interpolated the offending value into their message and the one `required_error` move to zod 4's `error` map with the same texts. The exported schema objects (`LessonFrontmatterSchema`, the artifact, config and record schemas) are now zod 4 instances, so a consumer that composes them with its own zod 3 schemas needs zod 4 too; no such consumer is known, which is why this ships as a minor rather than a major. `openai` 4.x declares an optional peer on zod 3 that is now unmet: pnpm prints one warning per install, here and in every consumer, and nothing loads, because Totem never imports `openai/helpers/zod`; the `openai` 6 bump that clears the warning is a follow-up. The MCP server's four tools publish their `inputSchema` through the SDK's zod-compat layer, and under zod 4 that JSON Schema no longer carries `additionalProperties: false` (descriptions, defaults, required lists and enums are unchanged); the server's runtime is the same, an unknown argument is stripped as before, and the issue objects a client receives on a refused call carry `origin` where they carried `received`. Deprecated-but-working zod APIs (`.strict()`, `.passthrough()`, `.datetime()`, `z.ZodIssueCode`, `{ message }` params) are untouched, `.datetime()`'s acceptance narrowing as stated above. Zod's own default error texts changed between the majors (for example "Required" now reads "Invalid input: expected string, received undefined", and an unknown key in a strict object reads `Unrecognized key: "x"` where it read `Unrecognized key(s) in object: 'x'`), so a Totem message whose tail quotes zod's wording, such as the action-policy refusal of a misspelled row or scope key, reads differently; Totem's own texts are unchanged.
