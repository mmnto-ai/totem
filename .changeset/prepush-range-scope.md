The managed pre-push hook grades the pushed range, not the working tree. Its lint step runs `totem lint --branch` and its strict-tier shield step runs `totem review --gate --branch`, so both read the branch-vs-base diff the push carries (`origin/<base>...HEAD`, else the local base) whatever the checkout holds uncommitted. The bare verbs read uncommitted edits first and fell to that scope only on a clean tree, so a dirty checkout had the gate lint and review edits that were not being pushed, skip the commits that were, and record a verdict over the wrong diff (measured on 2.14.0). The lint step probes `totem lint --help` for the flag, as the shield step already probes `totem review --help` for `--gate`, and a CLI without it runs the bare form behind a visible compat line naming the scope it reads; the shield's gate form carries `--branch` under the existing probe, since every CLI that answers it has had the flag since 1.53.9, and its compat form stays bare. The admission record already carries the resolved scope (`source`, `base`, `head`, `selectorForm`), so a gate run now records `branch-vs-base`, the base it diffed and the `--branch` selector. Disclosed: a dirty-tree push from a checkout whose base resolves nowhere now meets the base-resolution error the clean-tree path always had, with its `git fetch origin <base>` cure; and the range is the checkout HEAD's branch diff, not the refs git hands the hook on stdin, so pushing a branch other than the checked-out one still judges the checked-out head (mmnto-ai/totem#2793, the shared mechanism for the lint, review and legs steps). The committed `tools/pre-push` is regenerated to byte parity. Part of mmnto-ai/totem#3048.
