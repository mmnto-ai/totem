Managed git hooks reach consumers that extend them: a bare install rewrites a stale managed block in place when the trailer is an attested `totem:fork` extension, and `totem doctor` compares every managed block to the canonical on every install (mmnto-ai/totem#2753).

**The break it repairs.** A repo that appends its own blocks after a hook's end marker never received a managed-hook upgrade through `totem init`, and the doctor said nothing was wrong. Measured on mmnto-ai/liquid-city#1174: `totem init -y` at `@mmnto/cli` 1.123.0 reported "Upgraded reflexes to v13" while both `pre-commit` and `pre-push` kept their 1.121.0 managed text — the file carried five extension blocks after totem's end markers, and mmnto-ai/totem#2406's bounded-ownership rule declines a marker-headed file with any content after its end marker rather than clobber it. The decline is correct; being silent about it, and having no non-destructive way out, was not. `totem doctor` in the same tree printed `All 4 hooks installed`, because its currency compare returned early whenever `totemDir` was `.totem` or undefined — so on the default `totemDir`, which is nearly every repo, the row sensed marker PRESENCE and never compared the block. Presence was never the question that row is asked.

**What changed — the install arm.** `installGitHook` gains one arm, evaluated where the decline happens and before it. When totem owns the file through its end marker and the trailer is ATTESTED, the managed block is regenerated in place and the trailer is carried through byte-for-byte: the file becomes the canonical text plus `existing.slice(endIdx + endMarker.length)` with exactly one leading line terminator removed, so the seam does not gain a blank line on every install. Attested means the trailer's first non-blank line carries a full fork marker — `# <!-- totem:fork reason="…" owner="…" attested="…" -->`, parsed by core's `parseForkMarker`, with all three of `reason`, `owner` and `attested` present and non-empty. A BARE `totem:fork` marker does not qualify, and neither does one missing a field: for the parity detector a bare marker is enough to CLAIM a fork, but carrying a consumer's lines through a rewrite is a maintenance promise, and a promise needs a name, a reason and a date. Only the first non-blank line is read — an attestation below other lines vouches for what follows it, never for what precedes it. The action reports a summary line distinct from the whole-file drift-repair, naming the carry-through, so a consumer can read from the output that its extension survived. A second bare run is a no-op: the currency compare is the recomposed file, so an attested-trailer hook whose block already equals the canonical is `exists` with no write.

**What changed — the doctor arm.** The sensor behind the Git Hooks row (renamed `hooksStaleAgainstCanonical`, since `totemDir` is no longer what it is about) drops the default-`totemDir` early return and resolves the effective dir as the configured value else the installer's own `DEFAULT_TOTEM_DIR`. Every install now compares each hook's managed block — start marker through end marker, the same bounded region the installer owns — against the canonical this `@mmnto/cli` renders. A stale block is a `warn` naming the files and the dir, never a gate. The remediation follows the file's SHAPE, because the four shapes take four different cures: `--force` for a totem-owned whole file or a legacy hook with no end marker, a bare `totem hook install` for an attested extension (with the clause saying the extension is carried through unchanged), and the delete-and-re-append line for any other appended block, whose own lines `--force` would eat. Mixed shapes get one clause each.

**What did NOT change.** `--force` still overwrites the WHOLE file, trailer included — that is what it is for, and it stays the cure for a legacy hook. An unattested trailer still declines with today's message, byte for byte, and the file is untouched. The tier is still not an axis of the doctor's compare (the canonical is rendered at the tier the INSTALLED hook declares, so a `--strict` hook on a repo pinning no tier is never called drift and never handed a downgrading `--force`), a configured `totemDir` the installer refuses still leaves the row marker-only, and the bounded drift-repair of mmnto-ai/totem#2138 and the appended-block judgment of mmnto-ai/totem#2692 are unchanged in behavior. Session hooks (`.claude/hooks`, `.gemini/hooks`) are out of scope.

**Regression floor.** The carry-through is pinned by byte equality on both halves — the written block equals the canonical's block, the trailer slice equals the original trailer slice — on `pre-commit`, `pre-push` and `post-merge`, plus idempotence on a second run, plus `--force` still yielding the canonical alone. Each rejected attestation shape has its own test (unattested, bare marker, `reason` only), each asserting the file is untouched byte-for-byte. On the doctor side the case the early return hid is now a test in both spellings of the default (`{}` and `{ totemDir: '.totem' }`), beside a pass on a current block with an attested trailer, so neither arm can regress into presence-only sensing.

**MIGRATION — none.** No config key, flag, file location or output shape moves. Consumers with attested extensions receive the next template on their next bare `totem hook install` or `totem init`, with a summary line saying the extension was carried through; consumers with unattested trailing content see exactly what they see today. A consumer-side `--force`-then-re-append workaround can be retired: attest the trailer instead, and bare installs maintain the block from then on. One output change is deliberate and visible: a repo whose hooks are behind the running CLI's template now gets a `warn` on the doctor's Git Hooks row where it used to get `All 4 hooks installed` — that row was reporting presence, and it is now reporting currency.
