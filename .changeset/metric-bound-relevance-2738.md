Vector relevance is bound to a named metric: the hard-coded `1/(1 + _distance)` becomes a map keyed by the metric the store now explicitly queries with, and that metric is recorded in the query and in the index manifest (mmnto-ai/totem#2738).

**The borrow.** Synthesis § 2.1 C1 takes the DOCTRINE from LangChain's vector stores — a distance is meaningless without the metric that produced it, so the normalization belongs in a map keyed by a named metric rather than inlined at the call site — and NOT its constants. LangChain's euclidean constant presumes a non-squared distance; LanceDB's `l2` `_distance` is the SQUARED Euclidean distance, so borrowing that constant would have been wrong here. The doctrine transfers, the number does not.

**What changed.** `packages/core/src/store/relevance.ts` is new and exported from `@mmnto/totem`: `DistanceMetric` (`'l2' | 'cosine' | 'dot'` — the LanceDB TypeScript SDK's own three spellings, not `'ip'`), `DISTANCE_METRICS`, `VECTOR_DISTANCE_METRIC = 'l2'`, `assertDistanceMetric` (a `TotemError('CONFIG_INVALID')` naming the value and the allowed spellings, for values read off a record where the type cannot reach), `relevanceFromDistance(metric, distance)`, and `isRelevanceInRange(relevance)`. The map is module-private and each entry carries the SDK's own distance definition, the range on unit-norm vectors, and the resulting relevance range. Both vector query sites in `lance-search.ts` — `runVectorSearch` and the hybrid `runVectorLeg` — now chain `.distanceType(VECTOR_DISTANCE_METRIC)`, so the metric is a recorded fact in the query rather than the SDK default it happened to coincide with; `buildIndexManifest` writes the same constant as `vectorDistanceMetric` in `.totem/index-manifest.json`. `runVectorSearch` gains an `onWarn` parameter in the `runHybridSearch` position (`table, embedder, onWarn, query, …`), threaded from `LanceStore`'s existing warn sink.

**The measured bounds.** LanceDB SDK 0.26.2 returns the SQUARED Euclidean distance for `l2` — measured 3/3 on this repo's index: a self-hit is `0.00000000`, and a pair at cosine `0.845` came back as `0.3096`, which is `|a−b|²`, not `|a−b| = 0.5564`. On the unit-norm vectors this repo's embedding profile produces, `_distance ∈ [0, 4]`, so relevance `1/(1 + _distance) ∈ [0.2, 1]` — minimum observed `0.5022` over 3,795 hits. That interval is now pinned in tests (`d = 0 → 1`, `d = 4 → 0.2`, the measured pair `0.3096 → 0.7636`, and a sweep across the interval), so a floor set below `0.2` is visibly one that can never fire. `cosine` maps `1 − distance/2` over the SDK's documented `[0, 2]`; `dot` takes the same map on the SDK's own statement that "if the vectors are normalized … dot distance is equivalent to the cosine distance".

**The warning.** A relevance that leaves `[0, 1]` is a signal about the embedder, not about the query, so `relevanceFromDistance` stays a pure map and the judgment sits at the search call: each of `runVectorSearch`, `runHybridSearch` and `runFtsSearch` tallies breaches over one call and emits at most ONE warning per query, naming the metric, the count and a sample. Nothing is clamped, nothing is filtered, nothing throws — the rows come back exactly as they would have.

**What did NOT change.** No ordering moves: `relevance` still never enters a sort key, and RRF fusion is untouched. No `l2` relevance number moves — `1/(1 + _distance)` is what the map computes for `l2`, byte-identical to the deleted inline expression. FTS-only rows still carry no `relevance` at all (absence stays distinguishable from a weak signal), and a hybrid row still keeps its vector-leg relevance through fusion. The relevance floor, its default, and any per-item or pre-fusion variant are out of scope — that is mmnto-ai/totem#2727's question, and this slice deliberately leaves it open.

**MIGRATION — none.** No config key, flag, output shape or file location moves, and no relevance value changes. Two things can newly appear. `.totem/index-manifest.json` gains a `vectorDistanceMetric` field on the next `totem sync`; the field is optional and readers must tolerate its absence, so manifests written before this change stay readable and the schema id is unchanged. And a warning line can appear where none did before — but only for an embedder whose vectors are not unit-norm, and only far enough off to push a relevance outside `[0, 1]`. On a unit-norm profile it is unreachable.
