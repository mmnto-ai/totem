Vector relevance is bound to a named metric: the hard-coded `1/(1 + _distance)` becomes a map keyed by the metric the store now explicitly queries with, and that metric is recorded in the query and in the index manifest (mmnto-ai/totem#2738).

**The borrow.** Synthesis § 2.1 C1 takes the DOCTRINE from LangChain's vector stores — a distance is meaningless without the metric that produced it, so the normalization belongs in a map keyed by a named metric rather than inlined at the call site — and NOT its constants. LangChain's euclidean constant presumes a non-squared distance; LanceDB's `l2` `_distance` is the SQUARED Euclidean distance, so borrowing that constant would have been wrong here. The doctrine transfers, the number does not.

**What changed.** `packages/core/src/store/relevance.ts` is new and exported from `@mmnto/totem`: `DistanceMetric` (`'l2' | 'cosine' | 'dot'` — the LanceDB TypeScript SDK's own three spellings, not `'ip'`), `DISTANCE_METRICS`, `VECTOR_DISTANCE_METRIC = 'l2'`, `assertDistanceMetric` (a `TotemError('CONFIG_INVALID')` naming the value and the allowed spellings, for values read off a record where the type cannot reach), `relevanceFromDistance(metric, distance)`, and `isRelevanceInRange(relevance)`. The map is module-private and each entry carries the SDK's own distance definition, the range on unit-norm vectors, and the resulting relevance range. Both vector query sites in `lance-search.ts` — `runVectorSearch` and the hybrid `runVectorLeg` — now chain `.distanceType(VECTOR_DISTANCE_METRIC)`, so the metric is a recorded fact in the query rather than the SDK default it happened to coincide with; `buildIndexManifest` writes the same constant as `vectorDistanceMetric` in `.totem/index-manifest.json`. `runVectorSearch` gains an `onWarn` parameter in the `runHybridSearch` position (`table, embedder, onWarn, query, …`), threaded from `LanceStore`'s existing warn sink.

**The measured bounds.** LanceDB SDK 0.26.2 returns the SQUARED Euclidean distance for `l2` — measured 3/3 on this repo's index: a self-hit is `0.00000000`, and a pair at cosine `0.845` came back as `0.3096`, which is `|a−b|²`, not `|a−b| = 0.5564`. On the unit-norm vectors this repo's embedding profile produces, `_distance ∈ [0, 4]`, so relevance `1/(1 + _distance) ∈ [0.2, 1]` — minimum observed `0.5022` over 3,795 hits. That interval is now pinned in tests (`d = 0 → 1`, `d = 4 → 0.2`, the measured pair `0.3096 → 0.7636`, and a sweep across the interval), so a floor set below `0.2` is visibly one that can never fire.

All three metrics are additionally pinned BY MEASUREMENT rather than by the SDK's doc comment (`store/relevance.sdk.test.ts`): a throwaway LanceDB table of hand-chosen vectors is queried under the default and under each metric, and the returned `_distance` is asserted to 1e-6 before the map is applied. Measured against `q = [1,0,0]`: the default equals `l2` equals `[0, 2, 4, 0.8, 1]`; `cosine` `[0, 1, 2, 0.4, 0]`; `dot` `[0, 1, 2, 0.4, −1]`. So `dot` really is `1 − a·b`, agreeing with `cosine` on the four unit-norm probes and diverging on the fifth — the `2×`-scaled vector, where `dot` returns `−1` and the map yields `1.5`, the only out-of-range value in the whole matrix. The `dot` entry was previously justified by the SDK's prose alone; it is now the one thing in the map with an executable falsifier behind it.

**The warning.** A relevance that leaves `[0, 1]` is a fact about the data, not about the query, so `relevanceFromDistance` stays a pure map and the judgment sits at the search call: each of `runVectorSearch`, `runHybridSearch` and `runFtsSearch` tallies breaches over one call and emits at most ONE warning per query, naming the metric, the count and a sample. In `runHybridSearch` the tally runs over the vector leg's RAW rows, before RRF and before the `maxResults` slice, so a breach that loses the fusion is still counted. Nothing is clamped, nothing is filtered, nothing throws — the rows come back exactly as they would have.

The CAUSE the warning names is metric-specific (`OUT_OF_RANGE_CAUSE`), because it has to be: squared L2 is `≥ 0` by construction, so under `l2` no distance the SDK can legally return can push `1/(1 + d)` out of `(0, 1]`. A breach under `l2` is therefore an SDK or data fault — a negative `_distance`, the only input that can produce one, since a non-finite `_distance` is discarded before the map runs — and NOT the non-unit-norm embedder that the `cosine` / `dot` mappings really do break on. Naming the wrong cause would have sent an operator to inspect a vector norm that was never the problem.

**And the warning stays a warning downstream.** `GroundingItemSchema.relevance` is `z.number().min(0).max(1)`, which THROWS at the artifact write — so an out-of-range relevance would have turned "warn, never throw" into a hard failure one layer down, killing the very run the search returned unchanged. `buildGroundingBundle` now omits an out-of-range relevance from the item: the item survives, its `relevance` absent, exactly as an FTS-only hit's is, and the search layer has already warned once about the breach. Never clamped — a clamped number would launder a fault into a plausible-looking measurement. The schema bound is unchanged.

**What did NOT change.** No ordering moves: `relevance` still never enters a sort key, and RRF fusion is untouched. No `l2` relevance number moves for any distance the SDK can legally return — `1/(1 + _distance)` is what the map computes for `l2`, byte-identical to the deleted inline expression. FTS-only rows still carry no `relevance` at all (absence stays distinguishable from a weak signal), and a hybrid row still keeps its vector-leg relevance through fusion. The relevance floor, its default, and any per-item or pre-fusion variant are out of scope — that is mmnto-ai/totem#2727's question, and this slice deliberately leaves it open.

**One behavior change, disclosed.** Relevance is now computed only when `_distance` is a FINITE NUMBER. A `_distance` that is `NaN`, `±Infinity`, or not a number at all previously produced a `NaN` relevance (or, for `Infinity`, a `0`); it now produces NO relevance, and the hit's `score` comes from `_score` or falls back to `0`. Absence is the honest record — a `NaN` is not a measurement, and `1/(1 + -Infinity)` is `-0`, an in-range-LOOKING number that would otherwise have been recorded as a real measurement of zero similarity. Each input class (`NaN`, `Infinity`, `-Infinity`, a non-numeric value, and `Infinity` alongside a `_score`) has a test. LanceDB does not produce these values in normal operation; this is the fault path.

**What the floor makes of a fault.** `evaluateGroundingFloor` in `totem spec` applies the same `isRelevanceInRange` the bundle builder omits on, so one predicate governs both surfaces and the record and the judgment never disagree about the same hit — but the judgment keeps a distinction the record does not: a hit with NO vector leg (keyword-only) is floor-EXEMPT and one such hit saves the run, while a hit whose vector relevance FAILS the predicate is FAULTED — neither signal nor exemption. A fault cannot raise the best relevance, cannot be withheld as a measurement, and cannot save a run; a run whose every hit is faulted refuses outright ("nothing usable grounds this run"), and a refusal beside a fault names the faulted count. The bot round on this PR (Greptile P1) refuted the slice's earlier reading, which had counted a fault as exempt and disclosed the result as a "loosening on the fault path": an SDK fault is not evidence the way a keyword match is, and it must not authorize synthesis. So the refusal is TIGHTER than before this slice on the fault path, not looser — a free-text run whose only hits carry a negative relevance (a negative `_distance`, an SDK or data fault under `l2`) refuses, and says why. The floor's own default and calibration are untouched (mmnto-ai/totem#2727); this slice changes only which hits the floor may judge, and how.

(`evaluateGroundingFloor` takes the predicate as a parameter, supplied by its one caller from a dynamic `await import('@mmnto/totem')` — a static value import from the core barrel inside `commands/**` would pull LanceDB into every CLI startup, `--help` included. The predicate sits BEFORE `floor` in the signature because mmnto-ai/totem#2758 makes `floor` optional and a required parameter cannot follow an optional one; this PR merges after mmnto-ai/totem#2758 and is rebased onto it, as both edit `spec.ts`.)

Worth naming as NOT fixed here: the MCP `search_knowledge` reader still selects relevances with a bare `typeof === 'number'` check, so it would still read a `NaN` or an out-of-range value as signal. That is pre-existing behavior on a surface this slice does not touch (`packages/mcp/src/tools/search-knowledge.ts`, which has its own PR open), and it is a follow-up rather than a widening of this one.

**MIGRATION — none.** No config key, flag, output shape or file location moves, and no relevance value changes on any distance the SDK legally returns. Four things can newly appear. `.totem/index-manifest.json` gains a `vectorDistanceMetric` field on the next `totem sync`; the field is optional and readers must tolerate its absence, so manifests written before this change stay readable and the schema id is unchanged. A warning line can appear where none did before — under `l2` only on a negative `_distance`, which is a fault rather than a profile, and never on a healthy index. A grounding item can newly appear WITHOUT a `relevance` where the artifact write would previously have thrown on that same value — an omission is strictly better than the crash it replaces, and in-range relevances (including the boundary values `0` and `1`) are carried exactly as before. And a `totem spec` free-text run can newly REFUSE where it used to proceed: a run whose every hit carries an out-of-range relevance (the fault the warning reports) now refuses as "nothing usable grounds this run", and a fault beside a below-floor sibling no longer saves the run — the judgment is tighter on the fault path, never looser, and the refusal names the faulted count.
