A new verb: `totem resolve-threads <pr>` (mmnto-ai/totem#2841) — the deterministic, zero-LLM way past the merge-ready gate's unresolved-bot-threads predicate (mmnto-ai/totem#2800 predicate 2). It reads a PR's review threads through GraphQL, selects the unresolved, non-outdated threads rooted by a known review bot that carry **disposition evidence**, and resolves them through the `resolveReviewThread` mutation. **Dry-run by default**; `--apply` is the only path that mutates.

**The evidence rule** (R2) — the whole point of the verb: **an in-thread reply from a non-bot OR any non-bot PR-level (issue) comment created after that thread's root comment**; either suffices. The PR-level arm is deliberately not keyed to the round-disposition comment specifically — no deterministic reading distinguishes a disposition from other human prose, and a PR-level comment is the only lawful answer to a GCA thread (bot-protocols forbids replying to GCA in-thread). The consequence, stated because it is load-bearing: on a re-invoked round the operator's own trigger comment is non-bot evidence for every thread it postdates, which is exactly why the round disposition is posted BEFORE this verb runs. A thread with neither kind of evidence prints `skip:no-evidence` and is NEVER resolved, under any flag; under `--apply` a selected one makes the run exit 2 after the other rows were applied, so a silenced thread is impossible to miss.

**Two tests, not one.** Which threads get a ROW is core's four-name review-bot list applied to the thread's ROOT comment — the same closed set merge-ready's predicate 2 denies on, so the verb clears exactly what that gate reads and never a thread it did not deny. Who counts as a HUMAN REPLY is the wider test below; widening the root instead would have the verb resolving threads the gate never objected to.

**What counts as a bot** (the human-reply test) is wider than the review-bot list, because any GitHub App can comment and an App's comment is not a human answer: GraphQL `author.__typename === 'Bot'` (verified on mmnto-ai/totem#2839 — `greptile-apps` and `coderabbitai` answer `Bot` with no `[bot]` suffix on the login), a `[bot]`-suffixed login, or core's review-bot list; on REST, `user.type === 'Bot'`, the suffix, or core's loose pattern. A `github-actions[bot]` or Copilot-reviewer reply is therefore never mistaken for the human reply that would resolve a thread. A deleted account (null author) is deliberately NOT a bot — the reply it left was a human reply when it was written.

**One printed row per bot-rooted thread**, each carrying that thread's REST root comment id (the same id `totem triage-pr` prints as a finding's `rootCommentId`) and one of `resolve`, `skip:already-resolved`, `skip:outdated`, `skip:no-evidence`, `skip:not-selected`. Nothing is skipped silently. `--json` emits one document in exactly two shapes: `{repo, pr, apply, rows, summary}` on success, carrying the same rows the human lines print, and `{error, rows, exitCode}` on a failure, where `rows` is `[]` when the failure predates the plan and the built rows when it does not (the unmatched-id abort) — both shapes are locked by a test. That holds for a missing `gh` too: the precondition is probed through the verb's own seam (`gh --version`, added as the sixth shape of its exec allowlist and sent first) rather than by the CLI action's exit-before-the-command, so a script reading `--json` gets the failure document where it used to get three bare stderr lines (the PR's review round, greptile); the probe runs on the verb's 60 s gh timeout rather than the action's 3 s one, so a wedged gh stalls longer before that in-contract failure, disclosed. A structural test on the registration source keeps the action free of the precondition. Default selection is every evidenced bot thread; `--ids <comma-separated REST root comment ids>` narrows it, and an unmatched id aborts before ANY mutation (a typo must not silently narrow the batch). A human-rooted thread is never a candidate; a resolved or outdated thread is reported and never mutated; a deleted account's null author is never read as a bot identity, on either surface.

**The read is complete or it fails.** Both connections are paginated with explicit cursors (`reviewThreads` by cursor, a thread's `comments` by node id), capped at 20 pages each; a page that cannot be followed, a `gh` that did not answer, a GraphQL `errors` body or a payload that fails its Zod shape is a HARD failure — exit 1, nothing resolved, never a shorter list treated as the whole PR. The PR-level comment read is REST (`user.login` keeps its `[bot]` suffix, `user.type` is available), and its failure is equally hard: evidence cannot be derived, so no thread may be resolved. Bot identity comes from core's single `BOT_REVIEWER_IDENTITIES` definition — the exact closed-list test on the GraphQL surface, the loose pattern on REST. Every `gh` call goes through an injectable `GhRunner` seam (argv in, `{ stdout, exitCode }` out — never a shell string), so the tests run offline against checked-in captures, one of them a real read of mmnto-ai/totem#2839.

**Exit codes:** `0` the plan printed or `--apply` resolved everything it planned to; `1` a read that did not complete (nothing resolved) or `gh` absent; `2` an unmatched `--ids` entry, a mutation that failed (the run continues past it and names the count), or a selected thread skipped for want of evidence under `--apply`. A row is marked `applied` only when the mutation's own answer says `isResolved: true`; a clean `gh` exit over a null payload, a `isResolved: false` thread, or an unparseable body is a named per-thread failure. **The verb never posts a comment, a reply or a review** — `resolveReviewThread` is the only mutation it can issue, and the test that holds it is an ALLOWLIST, not a denylist: every argv the exec seam records must match one of the five shapes the verb may send (`repo view`, the three declared GraphQL documents with only their declared variables, and the paginated issue-comment read), with the mutation admissible only under `--apply`; a `pr review --approve`, a `gh api -X POST`, an `addComment` mutation or any other write fails the predicate, and a mutant test asserts that it does.

**The review-reply skill's `done` step gains the last operator-gated action** (all three distributed surfaces stay byte-locked): after the consolidated round-disposition comment posts — that comment IS the evidence the verb reads — run `totem resolve-threads` dry, show the plan, and only on the operator's explicit go run it with `--apply`.

**Not in this cut:** any change to a merge-ready predicate, any resolution without evidence, any reply or comment the verb posts itself, inbox-number (`#N`) selection, and any change to `totem triage-pr`'s read path.
