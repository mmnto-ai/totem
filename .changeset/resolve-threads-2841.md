A new verb: `totem resolve-threads <pr>` (mmnto-ai/totem#2841) — the deterministic, zero-LLM way past the merge-ready gate's unresolved-bot-threads predicate (mmnto-ai/totem#2800 predicate 2). It reads a PR's review threads through GraphQL, selects the unresolved, non-outdated threads rooted by a known review bot that carry **disposition evidence**, and resolves them through the `resolveReviewThread` mutation. **Dry-run by default**; `--apply` is the only path that mutates.

**The evidence rule** — the whole point of the verb: a thread is resolved only when the round answered it, in either of the two lawful shapes. `in-thread-reply` — a comment after the root whose author is not a review bot; or `pr-level-disposition` — a non-bot PR-level (issue) comment created AFTER the thread's root comment, which is the round-disposition comment the practiced routine posts, and the ONLY lawful answer to a GCA thread (bot-protocols forbids replying to GCA in-thread). A thread with neither prints `skip:no-evidence` and is NEVER resolved, under any flag; under `--apply` a selected one makes the run exit 2 after the other rows were applied, so a silenced thread is impossible to miss.

**One printed row per bot-rooted thread**, each carrying that thread's REST root comment id (the same id `totem triage-pr` prints as a finding's `rootCommentId`) and one of `resolve`, `skip:already-resolved`, `skip:outdated`, `skip:no-evidence`, `skip:not-selected`. Nothing is skipped silently, and `--json` carries exactly the same rows. Default selection is every evidenced bot thread; `--ids <comma-separated REST root comment ids>` narrows it, and an unmatched id aborts before ANY mutation (a typo must not silently narrow the batch). A human-rooted thread is never a candidate; a resolved or outdated thread is reported and never mutated; a deleted account's null author is never read as a bot identity, on either surface.

**The read is complete or it fails.** Both connections are paginated with explicit cursors (`reviewThreads` by cursor, a thread's `comments` by node id), capped at 20 pages each; a page that cannot be followed, a `gh` that did not answer, a GraphQL `errors` body or a payload that fails its Zod shape is a HARD failure — exit 1, nothing resolved, never a shorter list treated as the whole PR. The PR-level comment read is REST (`user.login` keeps its `[bot]` suffix, `user.type` is available), and its failure is equally hard: evidence cannot be derived, so no thread may be resolved. Bot identity comes from core's single `BOT_REVIEWER_IDENTITIES` definition — the exact closed-list test on the GraphQL surface, the loose pattern on REST. Every `gh` call goes through an injectable `GhRunner` seam (argv in, `{ stdout, exitCode }` out — never a shell string), so the tests run offline against checked-in captures, one of them a real read of mmnto-ai/totem#2839.

**Exit codes:** `0` the plan printed or `--apply` resolved everything it planned to; `1` a read that did not complete (nothing resolved) or `gh` absent; `2` an unmatched `--ids` entry, a mutation that failed (the run continues past it and names the count), or a selected thread skipped for want of evidence under `--apply`. **The verb never posts a comment, a reply or a review** — `resolveReviewThread` is the only mutation it can issue, and a test asserts the exec spy sees no `pr comment`, no `/replies` and no `reviews` write.

**The review-reply skill's `done` step gains the last operator-gated action** (all three distributed surfaces stay byte-locked): after the consolidated round-disposition comment posts — that comment IS the evidence the verb reads — run `totem resolve-threads` dry, show the plan, and only on the operator's explicit go run it with `--apply`.

**Not in this cut:** any change to a merge-ready predicate, any resolution without evidence, any reply or comment the verb posts itself, inbox-number (`#N`) selection, and any change to `totem triage-pr`'s read path.
