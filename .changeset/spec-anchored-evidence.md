`totem spec` publishes what it was ANCHORED on, refuses an unanchored topic it cannot ground, binds a hand-authored design record with `--from`, and the strict pre-commit gate reads that anchor (mmnto-ai/totem#2700).

**The break it closes.** `totem spec <slug>` on a free-text topic drafted a confident spec out of whatever the vector index returned — four runs in one week produced architectures for files, types and flags that do not exist — and the strict pre-commit gate accepted every one of them as workflow evidence, including a draft that was one newline long. The gate asked "did a `totem spec` run happen", which a confabulated run answers just as well as a grounded one. Nothing in the artifact said which it had been, so no reader could tell them apart.

**New artifact fields (`@mmnto/totem`).** The run artifact now publishes the discriminator instead of leaving it to be inferred:

- `grounding.anchor` — `{ kind: 'issue' | 'record' | 'free-text' | 'mixed', ref, sha256? }`. `ref` is `#<n>` for a bare number, the input as typed for `owner/repo#N` or a URL, the repo-relative path for a record, the topic text for a free-text run. `sha256` is REQUIRED iff `kind` is `record` (the digest of the very bytes rendered into the prompt) and refused otherwise. `mixed` is the honest fourth kind for issues and topics together.
- `grounding.floor` — the relevance floor the run was judged against.
- `relevance` on each `grounding.bundle` item — the vector-leg `1 / (1 + distance)`. ABSENT when the hit had no vector leg (FTS-only): "no signal" stays distinguishable from "weak signal", and the absence is the disclosure, never a zero. It enters `grounding.hash` with the item; the bundle's sort key and the recompute-from-the-surface invariant are unchanged.
- `admission.runMetadata.promptSource` — `'builtin' | 'override'`, derived at the writer before the code-blind directive is folded in.

Every field is optional, so artifacts written before this version parse byte-for-byte.

**The refusal.** A run with NO issue and NO record among its inputs now REFUSES when retrieval returns zero items, or when every signal-bearing hit is below the floor and no floor-exempt hit exists. It exits non-zero with a `GATE_INVALID` error naming the topic, the measurement (`0 hits` or `best relevance 0.xxx`), the floor's value AND its place (`searchRelevanceFloor in totem.config.ts (schema default 0.25 when unset)`), and every withheld candidate as `path — relevance 0.xxx` — exclusion is disclosed, never silently dropped. It returns before the orchestrator, so NO run artifact is minted. `--raw` is EXEMPT: it makes no LLM call and mints nothing, so it stays the way to inspect a weak topic's retrieval. A run that proceeds on a `free-text` or `mixed` anchor prints one warning that it is not gate evidence.

**`totem spec --from <record>`.** Binds a hand-authored design record: the LLM still runs (the record and the retrieved context are its input), the RECORD is the anchor — repo-relative path plus the sha256 of the bytes rendered into the prompt — and the record is NEVER written. The draft goes to `--stdout` or `--out`; with neither, it goes to stdout with a line saying a record derives no path. `--out` resolving to the record itself is refused before anything else runs, as are a missing, unreadable, empty or whitespace-only record and `--from` combined with positional inputs.

**`totem spec [inputs...]` is now optional.** The old required variadic made `--from` unreachable — commander refused the invocation before the command could bind a record. Calling `totem spec` with neither inputs nor `--from` is now the command's own error, carrying the usage line.

**The gate's new arm.** The strict pre-commit spec-evidence reader still selects the newest run artifact whose top-level `admission.runMetadata.caller` is `"spec"`, and still distinguishes "no spec artifact" (exit 2) from "the reader could not run" (any other status). It gains exit 3 — "the newest spec artifact is NOT evidence" — with the reason printed and both cures named. An artifact is evidence only when it is anchored `issue` or `record` AND its SUBJECT carries a shape:

- **TEMPLATE** (an `issue` anchor drafted by the built-in prompt): every heading in the command's promised skeleton is present and each is followed by at least one non-blank, non-heading line. The BLOCKED line names the missing or the empty heading.
- **DOCUMENT** (a `record` anchor, or an `issue` anchor drafted under an override prompt): at least one markdown heading followed by a non-blank, non-heading line. A draft written under a custom prompt cannot be held to the built-in template's headings.

On a `record` anchor the SUBJECT is the RECORD's bytes, re-read from `grounding.anchor.ref` at commit time (git runs hooks from the worktree top) — the draft is discarded on that path, so checking it would check nothing. The record's sha256 is compared and REPORTED in the evidence line (`record sha256 matches` / `record revised since binding (bound <8>, now <8>)`) as a SENSOR, never a gate: blocking on revision would price every fold of a design record at one LLM call. The reader's vocabulary — the required headings, the anchor kinds, the prompt-source spelling — is rendered from the one canonical constant via `JSON.stringify`, never re-spelled in the hook text. `tools/pre-commit` is regenerated in lockstep and stays byte-identical to the builder.

**MIGRATION — every pre-existing spec artifact reads as not-evidence.** The gate reads a missing `grounding.anchor` as "predates the anchored-evidence rule" and BLOCKS. In this checkout that is all of them: 158 run artifacts, 55 with `caller: spec`, 0 carrying `grounding.anchor`. The cure is one run of `totem spec <issue>` or `totem spec --from <record>`. On a strict-tier install this affects human commits too, not only agent commits — the arm fires on `is_agent OR TOTEM_HOOK_TIER=strict`.

**REACH — the arm's live population is small today.** Until mmnto-ai/totem#2706 (Claude Code agent detection is dead) is ruled, the strict arm fires only on installs that set `TOTEM_HOOK_TIER=strict` and on Cursor seats (`CURSOR_TRACE_ID`). This repo's own `tools/pre-commit` pins tier `standard`, so its exercise of record is the `sh`-executed test suite, not this repo's commits.

**FLOOR — at the default the below-floor refusal cannot fire on this embedder.** The vector-leg relevance is `1 / (1 + distance)`, which for unit-normalized vectors never drops below 0.333, so the default `searchRelevanceFloor` of 0.25 cannot be crossed. Measured twice on this repo's index (gemini-embedding, 768-d): when the design record was written, a nonsense query returned best relevance 0.548 (every hit 0.541–0.548) and a real query 0.706; on a freshly synced index during the build, the same nonsense query returned 0.359 and a relevant query (the design record itself, via `--from`) 0.337–0.354 — within 0.02 of the theoretical floor for both, so on that index the signal barely discriminates at all. The arms that fire today are therefore the zero-hit arm and the anchor arm; the below-floor arm becomes reachable only under a configured floor, and no value can be recommended from these two measurements. Calibrating the DEFAULT (and whether the formula must be metric-aware) is config-wide and MCP-visible, so it is filed as its own issue, mmnto-ai/totem#2727, with both measurements, not folded here.
