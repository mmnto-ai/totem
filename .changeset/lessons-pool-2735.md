Lessons are delivered again: every lesson retrieval asks the store for `type = 'lesson'` through one helper, and the partition that could never fire is deleted (mmnto-ai/totem#2735).

**The break it repairs.** `totem spec`, `totem shield` and `totem triage` each injected a RELEVANT LESSONS section that was always empty. mmnto-ai/totem#391 introduced lesson injection when lessons still lived inside the spec pool, partitioning them out by path. mmnto-ai/totem#431 moved lessons to `.totem/lessons/` under their own content type and re-keyed that partition to `type === 'lesson'` — but left the three callers fetching their pool with `typeFilter: 'spec'`. A `typeFilter` renders as exact equality on ONE content type, so a spec-typed pool cannot contain a lesson by construction: the partition was empty for every run since, and the three dedup searches that look for existing lessons before extracting new ones were blind for the same reason. Nothing failed, and no line said so — the count line printed `0 lessons` and everyone read it as an empty store. In this repo's own index, the very run that drafted the design for this fix was served `0 lessons` beside 5 specs; the same run after the change is served `10 lessons`.

**What changed.** One helper, `searchLessons(store, query, maxResults)` in the CLI, is now the ONE place the `lesson` content type is spelled for retrieval: it asks the store for `typeFilter: 'lesson'` and passes `query` and `maxResults` through untouched. Six retrievals route through it — the three `retrieveContext` lesson pools (`spec`, `shield`, `triage`) and the three dedup searches (`shield`'s learn-from-verdict block, `review-learn`'s and `extract`'s `retrieveExistingLessons`). The lesson pool is fetched in the same `Promise.all` as the spec, session and code pools, so the cure costs one concurrent read and no extra latency. `partitionLessons` is deleted rather than left unused: it is internal to a binary, nothing outside this package could call it, and a helper nothing calls is the shape that let this drift hide.

**Specs delivered are unchanged.** The `SPEC_SEARCH_POOL` over-fetch (20 in `spec`, 15 in `shield`, 20 in `triage`) existed only to leave room for a partition that never fired; each spec pool is now fetched at its own delivery cap, which is the same top-N-by-score the partition's slice produced. `spec`'s linked-store merge is untouched — linked results are still pushed, re-sorted by score and cut to the top 5 of the union. Lessons come from the PRIMARY store only, as they always did; a linked store is never asked for them.

**Regression floor.** The construction fact is pinned where it is true — a store seeded with one lesson row and one spec row answers a `lesson` query with only the lesson, and a `spec` query with no lesson — and each of the three `retrieveContext`s now has a test that seeds one row of each type, asserts both arrive, and asserts the store was asked for `'lesson'`. The next site that spells `'spec'` for a lesson search fails a test instead of quietly delivering nothing.

**MIGRATION — none.** No config key, flag, output shape or file location moves. The only user-visible difference is that the `Found: … N lessons` line, and the prompt section behind it, are no longer empty on an index that holds lessons. A project with no indexed lessons still reports `0 lessons`; run `totem sync` to index them.
