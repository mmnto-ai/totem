Lessons are delivered again: every lesson retrieval asks the store for `type = 'lesson'` through one helper, and the partition that could never fire is deleted (mmnto-ai/totem#2735).

**The break it repairs.** `totem spec`, `totem shield` and `totem triage` each injected a RELEVANT LESSONS section that was always empty. mmnto-ai/totem#391 introduced lesson injection when lessons still lived inside the spec pool, partitioning them out by path. mmnto-ai/totem#431 moved lessons to `.totem/lessons/` under their own content type and re-keyed that partition to `type === 'lesson'` — but left the callers fetching their pool with `typeFilter: 'spec'`. A `typeFilter` renders as exact equality on ONE content type, so a spec-typed pool cannot contain a lesson by construction: the partition was empty for every run since, and the dedup searches that look for existing lessons before extracting new ones were blind for the same reason. Nothing failed, and no line said so — the count line printed `0 lessons` and everyone read it as an empty store.

**What changed.** `searchLessons(store, query, maxResults)` — new in core (`store/search-lessons.ts`, exported from `@mmnto/totem`) — is the ONE place the `lesson` content type is spelled for retrieval: it asks the store for `typeFilter: 'lesson'` and passes `query` and `maxResults` through untouched. It lives in core rather than the CLI because core reads lessons too. Seven retrievals route through it: the three `retrieveContext` lesson pools (`spec`, `shield`, `triage`), the three CLI dedup readers (`shield`'s learn-from-verdict block, and `retrieveExistingLessons` in `review-learn` and `extract`), and core's `deduplicateLessons`, whose existing-lesson check asked for `spec` and so re-minted duplicates it should have dropped. `partitionLessons` is deleted rather than left unused: it is internal to a binary, nothing outside that package could call it, and a helper nothing calls is the shape that let this drift hide.

**The spec pools are requested exactly as before.** Each `retrieveContext` still asks for `SPEC_SEARCH_POOL` candidates (20 in `spec`, 15 in `shield`, 20 in `triage`) and still cuts them to the delivery cap with the partition's own slice — the request is byte-identical in query, type and width. That width is load-bearing rather than slack: `runHybridSearch` (`packages/core/src/store/lance-search.ts`) fetches `maxResults * HYBRID_OVERFETCH_FACTOR` per leg before RRF fusion, and hybrid is the live path whenever an FTS index exists, so the requested width IS the fusion window and narrowing it changes which specs survive, not merely how many are cut. Each `retrieveContext` now has a test asserting the spec request it sends, because request identity is the only thing that can pin "unchanged" against a real store. `spec`'s linked-store merge is untouched. Lessons come from the PRIMARY store only, as they always did.

**The grounding floor keeps the inputs it was ruled over.** `totem spec`'s refusal gate (mmnto-ai/totem#2700) judges the retrieval against a relevance floor, and an FTS-only hit — one with no relevance at all — is floor-exempt, with a refusal requiring zero exempt hits. The lesson partition was structurally empty when that gate was ruled and tested; a populated one would have let a keyword-matched lesson exempt nearly every free-text run and silently retire the refusal arm. So the floor now reads the spec, session and code partitions only, exactly as it did in practice before. Whether a lesson may ground a run at all is the mmnto-ai/totem#2727 floor arm's question, not this slice's. Delivery is not the gate: the `Found:` line and the run artifact still count every delivered lesson.

**Cost.** One more store read per command, and because every read embeds its query, one more embedding call: `spec` 3 to 4 (plus one per linked store), `shield` 3 to 4, `triage` 2 to 3. The reads run inside the existing `Promise.all`, so the cost is concurrent in wall-clock but not in quota.

**Regression floor.** The construction fact is pinned where it is true — a store seeded with one lesson row and one spec row answers a `lesson` query with only the lesson, and a `spec` query with no lesson — and each of the three `retrieveContext`s has a test that seeds one row of each type, asserts both arrive, and asserts the store was asked for `'lesson'`. The next site that spells `'spec'` for a lesson search fails a test instead of quietly delivering nothing.

**Evidence.** The same command, before and after: `totem spec 2735` — the issue-anchored run that drafted this slice's design — was served `0 lessons` beside 5 specs and 3 code chunks, and is served `10 lessons` (the `MAX_LESSONS` cap) beside the same 5 and 3 after the change; a record-anchored run over the committed design record reports the same 10. Replaying the round-1193 R1 harness (`.totem/fixtures/spec-runs-2026-09-02/scripts/r1-retrieve.mjs`, `--resident D:/Dev/totem`, this worktree's built dist, output to a scratch dir and not committed) over the resident's live artifact store delivers 10 lessons to every query — 56 of 56, where the round's own R1 measured 0 of 55. The denominator moved because the harness derives its corpus from the resident's live `.totem/artifacts/runs/`, which gained one spec-caller artifact after the fixture was exported; the committed fixture's denominator is still 55. Run artifacts are gitignored, so those replay numbers in the PR body are the reviewer-visible evidence.

**Not in this slice.** On the hybrid path `results[0].score` is an RRF artifact bounded near 0.033, so `deduplicateLessons`' 0.92 similarity threshold cannot fire and the existing-lesson check drops nothing even now that it looks in the right place — a pre-existing defect, separate from this one, for its own issue.

**MIGRATION — none.** No config key, flag, output shape or file location moves. The only user-visible difference is that the `Found: … N lessons` line, and the prompt section behind it, are no longer empty on an index that holds lessons. A project with no indexed lessons still reports `0 lessons`; run `totem sync` to index them. Worth naming: the lesson pool passes through no relevance gate and lands under a HARD CONSTRAINTS header, so on an index this size it saturates its cap on every run. A relevance gate for lessons is the mmnto-ai/totem#2727 floor arm's question.
