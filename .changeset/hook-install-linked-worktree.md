`totem hook install` from a linked git worktree no longer writes the hooks every worktree of the repository shares. The hooks directory git resolves for a linked worktree is the common one, so an install from a worktree on an older branch re-rendered the main worktree's pre-commit, pre-push and post-merge from that branch's templates, silently, with nothing at push time saying so. The installer now reads `git rev-parse --git-dir --git-common-dir` (offline: a `gitdir:` pointer whose target carries a `commondir` file), and from a linked worktree it prints one line naming the main worktree as the owner and skips the write, exit 0, so a consumer's `prepare` script is unaffected; `--force` still writes from a worktree for a user who means it. A submodule, whose two dirs are equal, is not a linked worktree. A bare repository, the one-worktree-per-branch layout with no main working tree, has nothing else to own the shared hooks, so its worktrees write them as before (read from the common dir's `core.bare`). The interactive `totem init` path and `--check` are unchanged, and the per-checkout session hooks are still regenerated. This repository's own `tools/install-hooks.js` takes the same arm, with `TOTEM_HOOKS_FORCE=1` as its force (mmnto-ai/totem#3122).
