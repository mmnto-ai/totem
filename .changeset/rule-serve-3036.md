**Added `totem rule serve <input.json>`, the serving writer: it lowers the records one input file names into `compiled-rules.json`, disposes of their legacy rows as the file says, refreshes the manifest and regenerates the exports, and its dry run writes nothing.** This is part B2 of mmnto-ai/totem#3036 (S6 step 2), with mmnto-ai/totem#3045 folded in as the stale-floor refusal.

- **The verb (`@mmnto/cli`).** `totem rule serve <input.json>` reads one `serving-input/1` file (strict: `schema`, `asOf`, `source`, `dispositions.legacyRow` `archive` or `remove`, `dispositions.stamp`, `floor[]`, `archive[]`; an unknown key anywhere is refused). Each floor record is lowered as its ledger rule id with `asOf` as its timestamp, so a re-run is byte-identical; under `archive` the legacy row stays at its index, archived with the reason `served by record <ruleId>`, and the lowered rows follow it; under `remove` they take its index; an entry with no legacy hash appends at the end. The `archive[]` rows are archived with the reason `<reason> (<ref>)`; one already archived is left untouched. Then the manifest is refreshed (`compiled_at` is `asOf`, `rule_count` counts every row as the full compile does) and the exports are regenerated. A second run with the same input changes nothing and writes nothing. `--dry-run` reads everything, writes nothing and prints the row-level report: per touched row its class and action, the class counts (they add up to the row counts), the active and archived counts and the blocking set before and after, the input's sha256 and `asOf`. `--json` emits the report as data. The verb is registered on the full build only; `rule author` and `rule promote` are not in the Lite build either.
- **The planner (`@mmnto/totem`).** `planServingWrite` is pure (no IO, no clock): the serving file's rows as plain parsed objects, the authoring ledger, the ingested records and the input in; the new rows and the report out. Rows it does not touch are the same objects, and the writer checks that each still serializes exactly as before planning before it writes anything. `ServingInputSchema` and `assertServingInputSupported` are exported with it.
- **The refusals.** Every one fires before any write and names the row or file at fault: an input file that is missing, unparsable or off its schema; a serving file that cannot be read or parsed, fails its schema or holds two rows with one `lessonHash`; a missing or corrupt manifest; a floor record with no effective ledger row, a row with no record block, another record path or another content hash; a record the lowering rejects (with its reason); a legacy or archive hash the file does not hold, a hash in both lists, or a legacy hash that disagrees with the record's `curation.sourceLesson`; a record-path row the floor does not name; `stamp: advisory`. `TotemErrorCode` gains `SERVING_INPUT_INVALID`, `SERVING_RECORD_MISMATCH`, `SERVING_FLOOR_STALE` and `SERVING_INVARIANT_BROKEN`.
- **The stale-floor check (mmnto-ai/totem#3045).** A floor record whose effective ledger row was admitted after the input's `asOf` is refused, as is an `authoredAt` that does not parse. The limit: the ledger writes `authoredAt` as a date with no time, which reads as midnight UTC, so a re-admission on the same day as `asOf` is not caught. The check is necessary, not sufficient; the other half is the rule of conduct that couples a re-admission to a re-scoring and a regenerated floor file.
- **The shared export helper (`@mmnto/totem`).** `exportLessonsForRules` is the one home of the export regeneration that `totem lesson compile --export`, `totem lesson archive` and `totem rule serve` run (untested rules dropped, archived rules shown with their reason); the first two now call it, with byte-identical output. `ingestRecord` in the CLI's intake library is exported so the writer's content hash is the intake's own.
- **Not built.** The advisory stamp mode (it waits on the ADR-110 reading), an exemption instrument and a `rule promote` guard. Nothing in this release runs the writer on this repository's own serving file.
