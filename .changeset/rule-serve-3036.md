**Added `totem rule serve <input.json>`, the serving writer: it lowers the records one input file names into `compiled-rules.json`, disposes of their legacy rows as the file says, refreshes the manifest and regenerates the exports, and its dry run writes nothing.** This is part B2 of mmnto-ai/totem#3036 (S6 step 2), with mmnto-ai/totem#3045 folded in as the stale-floor refusal.

- **The verb (`@mmnto/cli`).** `totem rule serve <input.json>` reads one `serving-input/1` file (strict: `schema`, `asOf`, `source`, `dispositions.legacyRow` `archive` or `remove`, `dispositions.stamp`, `floor[]`, `archive[]`; an unknown key anywhere is refused). `asOf` must be a strict instant, `YYYY-MM-DDTHH:MM:SS` with an optional fraction and an explicit zone (`Z` or `+HH:MM`/`-HH:MM`), naming a real calendar date and time; a zone-less date-time, a date alone, any other form `Date.parse` accepts, and an impossible value it would roll over (`2026-02-30`, `T24:00:00`) are refused. Each floor record is lowered as its ledger rule id with `asOf` as its timestamp, so a re-run is byte-identical; under `archive` the legacy row stays at its index, archived with the reason `served by record <ruleId>`, and the lowered rows follow it; a legacy row already archived (with any reason) is left byte-untouched and reported as `already-archived`; under `remove` the lowered rows take its index; an entry with no legacy hash appends at the end. The `archive[]` rows are archived with the reason `<reason> (<ref>)`; one already archived is left untouched. Then the manifest is rewritten (`compiled_at` is `asOf`, `rule_count` counts every row as the full compile does) and every export target is regenerated. `--refresh` is the deliberate repair after an interrupted run or an out-of-band edit: it skips the integrity refusal below and rewrites the manifest from the serving file as it is and every export, even when no row changes. `--dry-run` reads everything, writes nothing and prints the row-level report: per touched row its class and action (a `replace` lists the fields that differ, or `(key order)` when only the key order does), the class counts (they add up to the row counts), the active and archived counts and the blocking set before and after, the input's sha256 (of its text after CRLF to LF, so a CRLF checkout names the same run) and `asOf`, and what a real run would write. `--json` emits the report as data. The verb is registered on the full build only; `rule author` and `rule promote` are not in the Lite build either.
- **Integrity, write order, and no-change runs.** Before planning, the serving file's hash must be its manifest's `output_hash`; a file that changed after the manifest was written (a hand edit to any row, or a totem verb that rewrites rules without refreshing the manifest, such as a pack install, doctor's stale-rule archive or the first-lint promotion) is refused with nothing written, under the new code `SERVING_MANIFEST_STALE`, and the hint names the two deliberate repairs, `totem rule serve <input> --refresh` and `totem lesson compile --refresh-manifest --allow-record-rows`. Every write is then preflighted before the first one: the records attestation is computed and every export target is rendered in memory, its sentinels checked against its current text, so an export target with an unmatched sentinel (a start marker without an end, an end marker without a start, or an end before a start) refuses with nothing written (on a dry run too). A changing run then writes the serving file, the manifest and every export target, in that order, each through a same-volume temp file and a rename, including a target whose text already equals its rendering, as `lesson compile --export` and `lesson archive` do. A run whose plan changes no row writes nothing and compares no export, so the repository's own formatter pass over an export does not make the next run rewrite it; when the manifest's `records_hash` is not the current attestation it says so on one line naming `--refresh`, and still writes nothing. A second run with the same input on a complete result writes nothing. The residual window is an IO error between the writes, which can leave a later file unwritten (each file is whole, old or new, never torn); `--refresh` is its repair. `--refresh` does not repair a malformed manifest: the manifest preflight refuses a corrupt one with its own hint, and with atomic writes the writer can no longer produce one.
- **The planner (`@mmnto/totem`).** `planServingWrite` is pure (no IO, no clock): the serving file's rows as plain parsed objects, the authoring ledger, the ingested records and the input in; the new rows and the report out. Rows it does not touch are the same objects; before it writes anything, the CLI writer checks that each still serializes exactly as before planning. `ServingInputSchema`, `assertServingInputSupported`, `parseStrictInstant`, `parseAuthoredAt` and `STRICT_INSTANT_FORM` are exported with it.
- **The refusals.** Every one fires before any write and names the row or file at fault: a serving file its manifest does not attest (above); an input file that is missing, unparsable or off its schema; a serving file that is missing, cannot be read or parsed, fails its schema or holds two rows with one `lessonHash`; a missing or corrupt manifest (the hint names `totem lesson compile` for a lesson-only serving file, and a git restore of the manifest when the file holds record rows); a floor record with no effective ledger row, a row with no record block, another record path or another content hash; a record the lowering rejects (with its reason); a legacy or archive hash the file does not hold; a hash in both lists, including an archive hash equal to a floor rule id, on a first run and on every re-run; a legacy hash or rule id named twice in the floor, or an archive hash named twice; a floor rule id that collides with a non-record row; a legacy hash that disagrees with the record's `curation.sourceLesson`; a record row the floor names that is inactive, whether `archived`, `untested-against-codebase` or `pending-verification` (serving it again would re-activate it; the message names the status and any `archivedReason`; the hint gives two routes: to serve it again, remove the row by hand and re-run with `--refresh`; to keep it out, remove the row and drop its record from `floor[]`, then re-run with `--refresh`); a record-path row the floor does not name; an export target with an unmatched sentinel, including a lone end marker; `stamp: advisory`. A legacy hash absent from the file is refused, except on a re-run under `remove` when every record of its entry is already in the file. `TotemErrorCode` gains `SERVING_INPUT_INVALID`, `SERVING_RECORD_MISMATCH`, `SERVING_FLOOR_STALE`, `SERVING_INVARIANT_BROKEN` and `SERVING_MANIFEST_STALE`.
- **The stale-floor check (mmnto-ai/totem#3045).** A floor record whose effective ledger row was admitted after the input's `asOf` is refused. `authoredAt` is read as a date (`YYYY-MM-DD`, midnight UTC, the form the ledger writes) or a strict instant, each naming a real calendar value; a zone-less date-time, an impossible date or any other form is refused as unreadable. The limit: because the ledger writes a date with no time, a re-admission on the same day as `asOf` is not caught. The check is necessary, not sufficient; the other half is the rule of conduct that couples a re-admission to a re-scoring and a regenerated floor file.
- **The shared export helper (`@mmnto/totem`).** `exportLessonsForRules` is the one home of the export regeneration that `totem lesson compile --export`, `totem lesson archive` and `totem rule serve` run (untested rules dropped, archived rules shown with their reason); the first two now call it, with byte-identical output on a well-formed target. Changes they inherit: every target is rendered before the first is written, so a target with an unmatched sentinel now fails before any target is written, and that refusal names the target; a target holding a lone end marker (no start marker) used to receive an appended block after the stray marker, a malformed file, and now refuses with the marker named (`injectSentinelBlock`, so `exportLessons` refuses it too); and every export target is written through a same-volume temp file and a rename (`writeRenderedExport`, which `exportLessons` now also writes through), with the same bytes. `writeCompileManifest` likewise writes through the atomic writer at its one home, with the same bytes and mode and the same error on failure, so every manifest writer (lesson compile, lesson archive, rule promote, shield, rule serve) inherits it. `renderLessonExportsForRules`, `renderLessonExport` and `writeRenderedExport` are exported beside it. `ingestRecord` in the CLI's intake library is exported so the writer's content hash is the intake's own.
- **Not built.** The advisory stamp mode (it waits on the ADR-110 reading), an exemption instrument and a `rule promote` guard. Nothing in this release runs the writer on this repository's own serving file.
