A third gate in the gate engine: `merge-ready` (mmnto-ai/totem#2800) — a PreToolUse gate on the **Bash and PowerShell** tools that reads a five-point deterministic pre-merge floor off GitHub before `gh pr merge` runs, with zero LLM calls and zero writes. `totem gate install merge-ready` (or `--all`, or `totem init --gates=merge-ready`) installs it under a `Bash|PowerShell` matcher beside `transport-shield`.

**The evaluator lives in core** (`packages/core/src/merge-ready.ts`) beside the registry, and reaches `gh` only through an injected `GhRunner` seam (`(args: string[]) => { stdout, exitCode }`) — production spawns `gh` with an argv through `safeExec` (never a shell string), tests hand back checked-in captures. The read is ONE GraphQL query with explicit pagination cursors for reviews, review threads and the status-check rollup contexts (`MERGE_READY_QUERY`, plus a branch-keyed twin sharing its fragment for a payload that names no PR); there is no REST fallback, and a failed or incomplete read is UNEVALUABLE, never clean — the `reviews` and `reviewThreads` connections are held to the same bar as the check rollup: an answer in which either is missing, has no `nodes` array or no readable `pageInfo`, or carries a review without a state or a thread without its root comment, is a failed read with a named reason, never an empty complete list that lets predicates 2–4 pass (the PR's review round, greptile). The predicates, in order, the first failure being the reason: **1** the head commit's rollup is green — the rollup's commit is CHECKED against `headRefOid`, and a rollup off another commit, a PR that answered no commits, a rollup with no contexts connection, or a rollup reporting a non-SUCCESS state while listing zero checks are each unevaluable rather than green (a failing or still-running check denies; **zero checks passes as a FACT**, with the count in provenance and one stderr line, only in the two shapes where the rollup is consistent about it — absent entirely, or reporting `SUCCESS` over an empty list while COUNTING zero; a state that is `PENDING`, `FAILURE`, null or not a string is unevaluable, and so is a `totalCount` that is not a non-negative integer or that does not equal the number of contexts the read actually materialised (a claim the read did not deliver is an incomplete read, never a smaller green list) — branch protection owns "must have checks"), **2** no unresolved, non-outdated review thread whose ROOT comment is a known review bot, **3** no un-superseded `CHANGES_REQUESTED` (a later `APPROVED`/`DISMISSED` from the same reviewer supersedes; a `COMMENTED` does not), **4** no HIGH/Major bot inline that CURRENTLY applies to the head commit — read off `comment.commit.oid`, the commit GitHub re-points as the diff moves (the REST `commit_id` the charter names), with thread resolution deliberately IGNORED: a HIGH finding a human resolved by hand without touching the code still applies to what would merge, while the same finding pointing at an older commit does not deny. The severity read is EXACT-BY-MARKER: each bot's own structured label and nothing else — greptile's badge `alt="P0"`/`alt="P1"`, quoted either way or unquoted (P2 and below are not high), GCA's `![high]` image alt (there is no `critical` arm: that asset 404s and GCA's rubric tops out at `high`), and CodeRabbit's emphasis-wrapped `_🔴 Critical_` / `_🟠 Major_` / `_⚠️ Potential issue_` cell labels. Which of those forms are corpus-OBSERVED and which are documented-but-unobserved is stated per arm in the source. Prose is never read, and neither is CODE: fenced blocks (any backtick or tilde run), inline code spans (any backtick run), `<pre>` blocks and CommonMark's indented blocks are all stripped first, so a bot that QUOTES a marker — a CodeRabbit Minor whose suggestion block quotes this gate's own docstring — cannot false-deny the gate's maintenance PR. Per ADR-109 this non-exact read ships a STATED false-positive budget and the fixture that measures it: ZERO high reads over the benign corpus in `gate-fixtures/merge-ready/benign-corpus-bot-inlines.json` — all sixteen bot inline threads on mmnto-ai/totem#2820 through mmnto-ai/totem#2839, each carrying the severity its own bot declared, asserted thread by thread. The word-based read this replaced flagged a greptile **P2** finding as HIGH through the word "critical" in its explanation, **5** GitHub's own `mergeStateStatus` (`CLEAN`, `HAS_HOOKS`, `UNSTABLE` pass; `BEHIND`, `DIRTY`, `BLOCKED`, `DRAFT` deny; `UNKNOWN` and any value the gate does not read are unevaluable). No bot review present passes 2–4 as a fact, never a failure. The head sha is read once and every later page checked against it — a head that moved mid-read is unevaluable, named. Every verdict keeps the shipped ADR-109 shape (`disposition: allow | warn | deny`, `reason`, `provenance`) and carries its evidence in a new optional `provenance.detail`: head sha, check counts, thread counts with `pagesRead`/`complete`, `changesRequestedBy`, `highInline`, `mergeStateStatus`, `evaluatedAt` and the `gh <version>` that answered.

**The tier argument reaches the engine.** `totem gate check` gains `--tier strict|pilot` (default strict, validated at the boundary — an unknown value throws rather than defaulting enforcement), and `evaluateGate` gains an optional `GateContext` (`tier`, `ghRunner`, `env`, `writeStderr`). The split is PER GATE and applies to the UNEVALUABLE class only: merge-ready `warn`s under pilot where a read failed to derive, `freeze-check` and `transport-shield` read no tier at all and keep failing closed at every tier. A predicate that actually FAILED is `deny` at both tiers — the wrapper's disposition map owns what that costs — and the predicates are read BEFORE the unreadable-commit arm, so a failing check beside a bot HIGH inline whose `comment.commit` is null denies as predicate 1 rather than warning as unevaluable under pilot; that arm still preempts predicate 5, its place in charter order (the PR's review round, CodeRabbit). A connection-level unreadable answer — a missing or malformed connection, a failed page, a moved head — still preempts every predicate: a read that did not complete has no facts to deny on. `TOTEM_MERGE_GATE_OVERRIDE=1` (read per evaluation) yields `allow` plus one stderr audit line naming the repo, the PR, the head sha and the predicates that would have denied. No path is silent degradation: every unevaluable arm — gh absent or unauthenticated, an API error or rate limit, a GraphQL error in a 200 body, a page that failed, a moved head, `mergeStateStatus: UNKNOWN`, a read past the 20-page cap — is named on stderr under BOTH tiers; only the exit code differs.

**One definition of the review-bot identities.** New core module `packages/core/src/bot-identity.ts` exports `BOT_REVIEWER_IDENTITIES` (coderabbit, gemini-code-assist, greptile, plus GitHub's `github-code-quality`) with, per identity, the loose `loginPattern` triage matches a REST-shaped login with, a CLOSED `exactLogins` list for the GraphQL surface — where `author.login` carries **no `[bot]` suffix** (`gemini-code-assist`, `greptile-apps`), the trap that made two copies dangerous; membership, not a pattern, so a human account like `greptile-fan` can never satisfy a gate's read — and the exact logins that resolve to a Layer-B actor id. `packages/cli/src/parsers/bot-review-parser.ts` and `packages/core/src/capability/review-catch.ts` now import it and declare no list of their own; a parity test fails if either grows one back. The greptile login was fixed BY OBSERVATION (`greptile-apps[bot]`, read off mmnto-ai/totem#2821, mmnto-ai/totem#2827, mmnto-ai/totem#2831 and mmnto-ai/totem#2834 on 2026-09-07), not from either stale copy. Behaviour of both consumers is unchanged: `isBotComment`, `detectBot` and `resolveActorId` classify exactly what they classified before, `alice-greptile` included.

**The wrapper recognises `gh pr merge` at command position.** `.claude/hooks/gate-wrapper.cjs` gains a `merge-ready` projection: one quote-aware walk reads the shell's grammar the way core's `transport-shield` scanner does — it skips `$(( … ))` / `(( … ))` arithmetic whole (so `$((1<<2))` is a shift, not a heredoc), discards a `#` that begins a word to end-of-line (a comment is not a command, and a `<<note` inside one opens nothing), blanks a PowerShell `<# … #>` block comment whole for the same reason, honours a backslash-newline as the line continuation the shell removes (so `gh \<LF>pr merge 5` is still a merge), and QUEUES every `<<` on an operator line so `cat <<A <<B` has both bodies read as data — blanks those bodies (quoted, bare or `<<-` delimiter, unterminated ones read to the end), then splits the remaining text on unquoted separators (`;`, `&`, `|`, a newline, `(`/`)`, `{`/`}`) and tokenizes each segment. The gate therefore fires on `gh pr merge` at the start of a segment and after `&&`, `;`, `||`, `|`, a newline, and behind the shell's own command-position words — the reserved words `do`, `then`, `else`, `if`, `elif`, `while`, `until`, `time`, `coproc` and `!`, the builtins `exec`, `command` and `eval` (on an unquoted operand), and any run of `NAME=value` assignment prefixes, so `if gh pr merge 5; then …`, `time gh pr merge 5` and `GH_TOKEN=x gh pr merge 5` are judged (before the PR's review round only `do`/`then`/`else`/`!` were skipped, and a merge used as an `if` condition or behind an assignment prefix went unjudged — greptile) — including a real merge that FOLLOWS a heredoc or an arithmetic expansion — and never inside a quoted string, a heredoc body or a comment (`echo "gh pr merge"`, `cat <<EOF` … `gh pr merge 5` … `EOF`, and `echo hi # gh pr merge 5` all pass through without spawning). **Every merge in a compound command is judged**, each PR on its own facts: `gh pr merge 7; gh pr merge 8` spawns the engine twice; the first strict deny or fail-closed arm exits, while a warn or a `--pilot` deny prints its line and the next merge is still judged (the same round — judging only the first let the shell run the second unjudged). The misses that stay disclosed, all in the safe direction: a wrapper program that takes operands first (`sudo`, `timeout 30`, `npx`, `env`) or one of the skipped builtins carrying a flag (`command -p`, `exec -a x`) puts something other than `gh` at the segment's front, so the position anchor does not see it; a merge handed over as one quoted word (`eval "gh pr merge 5"`, `bash -c "…"`) is data to the walk; a backtick command substitution and a leading redirection keep the merge inside another word's segment; and PowerShell's own quoting (backtick escapes, here-strings) is not modelled — the walk reads POSIX quoting for both tools. Two contrived false FIRES are disclosed too, surfaced when every segment began to be judged: a bash array assignment spelling a merge (`A=(gh pr merge 8)`) and a `case` pattern `gh pr merge)`, which projects an empty argv onto the current branch; the audited override is the way past either. The loop shares ONE 30-second budget across its payloads, so the wrapper's wall time is what it was before the loop and a merge that cannot be judged inside it fails closed rather than running into the host's own hook-kill. An argument the walk cannot resolve — an unexpanded shell variable, `gh pr merge $PR` — rides as `unresolvedTarget`, which the engine treats as unevaluable before any read rather than guessing a branch named `$PR`. From that segment's argv it projects `{ repo, pr | null, branch?, headSha? }` (a number, a PR URL, a branch, `-R`/`--repo`/`--repo=`; value-taking flags consume their value so `-b "…" 42` still finds the target; nothing named → `pr: null` plus the current branch), filling `repo` from `GH_REPO` then the git remote, and the head sha from `git rev-parse HEAD`. Anything else on a Bash/PowerShell envelope is not-applicable → exit 0 without spawning; a malformed payload is `GATE_INVALID` → the wrapper's existing fail-closed arm. The wrapper also passes the child's stderr through VERBATIM in every arm, `allow` included — that is the channel merge-ready's audited-override line and its zero-checks fact travel on, and printing it only on failure kept exactly the lines that must never be silent out of the transcript.

**The `--tier` coupling, stated:** the wrapper forwards `--tier <tier>` to `gate check` ONLY when the baked tier is not `strict`. `strict` is the engine's default, so a strict entry — every default install — sends no new option and keeps working against a Totem CLI at 2.2.x, including the PATH-resolved CLI a fresh clone falls back to (mmnto-ai/totem#2822); forwarding it unconditionally made every gated command exit "unknown option" into the fail-closed arm on such a CLI, which is the bootstrap self-block again. A `--pilot` install does send `--tier pilot` and therefore requires a CLI at 2.3.0 or newer — this cut; `totem gate install --pilot` and `totem init --gates=… --pilot` both print that floor at install time, and the wrapper's PATH-arm provenance line names 2.3.0 instead of 2.2.0 when the entry is baked `--pilot`.

**The fixtures are checked in** under `packages/core/src/gate-fixtures/merge-ready/` with a README naming each PR, its capture instant and the query: real `gh api graphql` captures of mmnto-ai/liquid-city#363 (green rollup, one unresolved HIGH inline from `gemini-code-assist` on the head commit), mmnto-ai/totem-strategy#1251, and mmnto-ai/totem#2827 — the corpus witness for predicate 4, whose bot HIGH comment has `commit.oid` = the head while `originalCommit.oid` is an older commit — all taken by running the real evaluator with a teeing runner so the query in the capture is the one it sends. All three PRs are merged, so GitHub answers `mergeStateStatus: UNKNOWN` for each — every `mergeStateStatus`, the pagination arms (a clean first page with a dirty second page denies; a failed second page is unevaluable), the stale-commit vs head-commit HIGH inline pair, a superseded `CHANGES_REQUESTED`, zero checks, a moved head, a rate-limit exit and an absent `gh` ride as clearly labelled synthetic fixtures beside them.

**Not in this cut:** installing the gate anywhere (it stays opt-in repo policy through `gate install` / `init --gates=`), the strategy parity-manifest row, retiring the user-level `merge-gate.cjs` prototype, and any change to the `allow | warn | deny` contract or to the wrapper's exit-code map.
